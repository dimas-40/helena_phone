# 판의 전환 — 오버레이 키트와 런타임 후보정, 그리고 AI 디렉터

오늘은 태블릿(Tab S9)에서 영상 제작의 판 자체가 뒤집히는 이야기를 정리했다.

결론부터 한 줄로:

> **옛날에는 사람이 GUI 앱(APK/PWA)을 클릭해서 수작업했다. 지금은 AI 디렉터(Claude Code + Grok)가 CLI에서 판을 짜고, APK를 "사람 손"처럼 조작한다. 목표는 "AI를 쓰되 AI 같지 않은" 연출 — 진짜 사람이 실수하면서 만든 것처럼.**

---

## 1. 우리는 어디까지 왔나

태블릿(dimas-40)은 "교육방송 스튜디오"다. 5개 EAE 레포(eae-image·eae-video·eae-music·eaekr·eaeuniv)가 방송국의 부서고, Claude(상주)는 공장의 80%, Grok(용병)은 천장의 20%(최대 4장)를 맡는다. 이 분담은 이미 잠금 상태다.

## 2. 오버레이 키트는 "사람 손"이다

dtslib-apk-lab 레포를 파싱하니, 내가 예전에 만들었던 오버레이 키트 APK들이 그대로 있었다.

- **parksy-axis** — 방송 단계 오버레이 (FSM, 6테마, 4방향)
- **laser-pen-overlay** — S Pen 판서 오버레이
- **parksy-studio** — 방송 스튜디오 전체 APK (녹화+카메라오버레이+BGM+트리머+cloud-appstore 런처)

이 APK들은 **녹화 중에** 화면 위에 방송 효과를 얹는 도구다. 그리고 중요한 건, 이 APK들은 **터미널에서 조작할 수 있게** 이미 만들어져 있다 — 설정 파일을 직접 쓰거나(axis), WebSocket으로 명령을 받거나(glot), 터치 주입(TouchInjectionService)이 달려 있다.

## 3. 후보정은 "빌린 연산"이다

dtslib-cloud-appstore에는 런타임 브라우저 후보정 앱이 있었다.

- **lecture-long** v4.0 — 16분 강의를 12분으로 자동 변환
- **lecture-shorts** v2.2 — 강의를 9:16 숏폼으로 (WebCodecs로 10~30배 빠름)

이것들이 브라우저(FFmpeg.wasm/WebCodecs)를 빌린 이유는 단순히 "ffmpeg가 없어서"가 아니다. **공짜 플랫폼 API + 브라우저 GPU를 빌려서, 태블릿 CPU 한도보다 빠르게** 돌리기 위해서였다. 우회가 아니라 연산 아웃소싱이다.

## 4. 판의 전환

옛날 이 앱들을 만들 때는 **AI가 없었다.** 사람이 직접 앱을 열고, 클릭하고, 효과를 골랐다.

지금은 다르다. CLI에서 AI가 디렉터 역할을 하고, proot Ubuntu와 안드로이드가 브릿지로 이어져 서로 왔다 갔다 한다. 저장소도 마음대로 쓴다.

그러니까 **실행층이 바뀐다:**

| | 옛날 | 지금 |
|---|---|---|
| 디렉터 | 사람 손 | AI 디렉터 |
| 실행층 | APK/PWA GUI | CLI + FFmpeg |
| 오버레이 조작 | 손가락 | AI (파일·WebSocket·터치주입) |
| 후보정 연산 | 태블릿 CPU | 브라우저 GPU 빌려쓰기 |

## 5. 핵심 원칙 — "AI를 쓰되 AI 같지 않게"

가장 중요한 지점은 여기다.

FFmpeg로 뽑은 영상은 **너무 매끈하고 기계 같다.** 진짜 사람이 만든 것처럼 보이려면 — 실수도 하고, 손도 움직이고, 실시간으로 오버레이가 떠야 한다.

그래서 오버레이 키트 APK가 본체다. 에이전트가 터미널에서 그 APK를 **마치 사람 손처럼** 조작해서, 인간 같은 움직임을 만들어낸다. FFmpeg는 그걸 이어붙이는 접착제일 뿐이다.

**진정성이 해자다.** 매끈한 AI 렌더는 슬롭으로 보이고, 실수·손동작·실시간 오버레이가 진짜로 보인다.

## 6. 앞으로

1. 에이전트→APK 조종 프로토콜 확정
2. 오버레이 키트 APK를 온디바이스 도구 슬롯에 배치
3. 브라우저 런타임 vs FFmpeg 경계 확정
4. lecture-long/shorts 마감 규격을 규격서로 정리

오늘 정리한 관계도는 GitHub Pages의 인터랙티브 노드 그래프로 함께 올라간다.
