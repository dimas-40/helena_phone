## 함정 6 — 2026-08-22 신규 확인 (Claude Sonnet 5 세션에서 실측)

**지도캡차(dkaptcha, POI 클릭형)와 카카오 계정 SMS 본인인증을 같은 벽으로 착각.**

두 개는 로그상 똑같이 "⚠️ 캡차 iframe 감지"로 찍혀서 구분이 안 됨 — 근데 완전히 다른 종류:

| | 지도캡차 (dkaptcha) | 계정보안 SMS 본인인증 |
|---|---|---|
| 목적 | 봇 여부 판별 | 계정 도용 여부 판별 |
| 풀이 방법 | 좌표 클릭 (사람 시각 판단으로 자동화 가능) | **실제 등록 전화번호로 SMS 코드 수신 필요** |
| URL 특징 | 일반 로그인 URL 그대로 | `#selectContactPhoneNumberForActionPenalty` 포함 |
| 자동화 가능 여부 | ✅ 가능 (screenshot relay + 좌표) | ❌ **불가능** — 기술로 우회하면 안 되는 영역 |

**이 세션이 실제로 저지른 실수**: SMS 본인인증 화면을 보고 "팝업이 열렸나?"로 오판, 화면이
안 바뀌는데도 좌표를 3번 연속 blind로 재시도함(508,379 / 600,380 / 508,548). 사람이 개입해서
멈추기 전까지 못 알아챔.

**판단 기준 — 반드시 이 순서로 확인**:
1. 화면 텍스트에 "평소와 다른 로그인", "본인인증", "추가 인증"이 있으면 → **즉시 정지**
2. `page.url()`에 `ActionPenalty`가 포함되면 → **즉시 정지**
3. 이 경우 좌표 재시도 절대 금지. 실제 사람에게 SMS 코드 요청하고 대기
4. 이건 계정당 1회성이다 — 한 번 통과하면 세션/쿠키가 기억하므로, 다음부터는 이 벽 자체가 안 뜸

**왜 우회하면 안 되나** (`_notebook/17-merged-chronicle.md`에 이미 명문화됨):
> "관공서 본인인증 같은 건 애초에 기술로 우회할 수 없는 영역임을 인지 — 법적 동의 확인,
> 대면 신원 확인은 구조적으로 우회 불가." (헌법 제1조 — 루팅/Shizuku 전면 금지와 같은 급의 원칙)

## 함정 7 — 2026-08-22 신규 확인: 뜸한 계정 자체가 구조적 고위험

**"주계정(자주 쓰는 계정)이면 문제없이 됐을 것"이라는 박씨의 관찰이 정확했다.**

카카오 부정로그인 탐지는 "이 로그인이 평소 패턴과 다른가"를 보는데, 아래 3개가 겹치면
최대 위험도로 잡힌다 — dtslib1k/dtslib2k가 정확히 이 조합이었다:

1. **계정 자체가 뜸함** — 블로그 발행용으로 만들어놓고 거의 안 씀. "평소 패턴"이라는
   비교 기준 데이터 자체가 없어서, 뭘 해도 이상 신호로 튀기 쉬움
2. **완전히 새 기기 지문** — Xvfb+Ubuntu에서 처음 뜬 Chromium(`device/Linux_x86_64`).
   카카오 입장에선 "한 번도 본 적 없는 기기"
3. **자동화스러운 패턴** — 폼 채우는 속도/타이밍이 기계적으로 보일 수 있음

주계정은 평소 실제 기기로 매일 로그인해서 "신뢰기기" 이력이 쌓여있으니 새 기기가 붙어도
상대적으로 덜 튄다. 뜸한 계정은 비교할 "평소"가 없어서 첫 시도부터 최대 경계로 감.

**실측 결과 (같은 세션, 2026-08-22)**: dtslib2k 계정에 지도캡차 통과 → SMS 본인인증까지
갔다가, 코드 재발급/재시도가 몇 차례 겹치자 카카오가 계정 자체를 **2시간 잠금** 처리함
(`"시도 횟수를 초과했습니다. 2시간 후에 다시 시도해 주세요."`). 함정 1(반복 로그인)이
"뜸한 계정"이라는 조건과 만나면 일반 계정보다 훨씬 빨리, 훨씬 세게 터진다.

**대응 원칙**:
```
- 뜸한 계정을 자동화 대상으로 잡을 땐 "바로 자동화"가 아니라
  1) 사람이 평소 쓰는 정상 기기/브라우저로 먼저 한 번 로그인해서 신뢰기기 이력을 만들고
  2) 그 세션 쿠키를 자동화 프로필로 넘기는 순서로 간다.
- 이미 SMS 본인인증 벽에 걸렸다면 재시도/재발급 요청을 남발하지 않는다
  (재발급 자체가 "시도 횟수"에 포함되어 잠금을 앞당길 수 있음).
- 2시간 잠금이 뜨면 그 즉시 전면 중단 — 같은 계정으로 어떤 시도도 하지 않는다.
  카운트다운이 재시도로 리셋/연장될 수 있다.
```

## 공통 원칙 — 모델이 반드시 기억할 것

```
1. 실패 = "아직 안 됨"이 아니라 "원인을 모른다"는 신호다. 재시도 전에 원인부터 특정한다.
2. 에러 메시지를 액면 그대로 믿지 않는다 — 실제 상태(DOM, URL)를 직접 확인한다.
3. "같은 아이콘/같은 로그로 찍힌다"고 "같은 문제"는 아니다 — 화면 텍스트/URL로 종류를 구분한다.
4. 기술로 우회하면 안 되는 벽(신원 인증, 법적 동의)과 우회해도 되는 벽(봇 감지 캡차)을 구분한다.
5. 모르면 사람에게 물어보고 멈춘다 — 자원(쿨다운, 시간, API 호출)을 태우면서 계속 찍는 건 해결이 아니다.
```

## 함정6 보완 — 2026-08-22 실측: ADB로 SMS 무인 판독 가능 (완전 자동화 성공)

**전제가 다르면 "우회 불가"가 "우회 아님"으로 바뀐다.** 함정6의 "본인인증은 우회 불가" 원칙은
여전히 유효하지만, 딱 한 조건이 충족되면 사람 개입 없이 자동화할 수 있다:

> **박씨 본인 소유의 실제 폰 + 이미 승인된 ADB 접근이 있을 때만**

이 경우 SMS 인증 자체는 정상적으로(우회 없이) 통과시키고, 그 코드를 "사람이 폰 보고 불러주는"
중간 단계만 `adb shell content query --uri content://sms/inbox`로 대체한다. 우회가 아니라
전달 경로의 자동화.

**실측 (eae_kr@kakao.com, 2026-08-22)**: SMS 발송 → ADB로 문자함 조회 → 타임스탬프 검증
(오래된 인증문자와 혼동 주의) → 코드 추출 → Playwright에 주입 → 로그인 성공, 60초 이내.

**상세 절차/코드**: `~/termux-bridge/docs/05-adb/ADB-SMS-AUTO-VERIFICATION-2026-08-22.md` (WSL 레포)

**적용 조건 재확인 — 이거 없으면 이건 그냥 헌법 위반**:
- 타인 계정 금지 / ADB 미승인 기기 금지 / 폰 소유자 확인 없이 진행 금지
