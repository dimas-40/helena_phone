Parksy 레이블 — 목표 확정과 진짜 병목 (2026-10-03)

표기 규칙: [실측] = 직접 명령으로 확인 · [Boss] = Boss 발화 원문 · [기록] = 기존 문서 인용 · [미검증] = 아직 안 해봄

이 문서는 Boss가 지금 무엇을 하려는지를 정확히 남기기 위한 것이다.
117(3노드 기술 인벤토리)의 목적 편이다. 기술은 117, 왜/무엇은 여기.

0. 한 줄

Boss의 목표는 “폰에서 음악이 된다는 증명”이 아니었다.
퍼블릭 도메인 원곡 → 내 편곡 → 내가 만든 가상악기 → 내가 만든 가상보컬 → 실제 레이블.

이 문서는 그 목표를 기준으로 난이도를 다시 정렬한 기록이고,
그 과정에서 우선순위가 하나 뒤집혔다(아래 §5).

1. 목표 — Boss 발화 원문 [Boss]

“폰 하나로, 코드 안 치고, 제일 싼 모델로 된다는 걸 증명 이라면 → 어려운 게 목표야.
퍼블릭 도메인 기준으로 모든 작곡 편곡까지 다 해가지고 내 가상악기까지.
내가 만드는 가상악기에 내가 만든 가상 보컬까지 만들어서 실제 진짜 스튜디오를 만들 거라고 레이블“

그리고 1년 전 이력에 대해:

“옛날에 이거는 내가 코딩 지식이 하나도 없을 때 1년 전에 시도하다가 큰 그림만 걸어 놓고 빠진 거고
지금은 실력이 이렇게 좋아졌잖아. 이제 할 수 있어.“

해석: 1년 전 중단은 판단 착오가 아니라 실행 수단 부재로 인한 보류였다.
지금은 실행 수단이 생겼다. → 이번엔 그림이 아니라 부품을 만들어야 한다(§8).

2. 이건 새 계획이 아니다 — 레포에 이미 있다 [기록]

parksy-audio docs/에 이미 선언돼 있다. 내가 읽은 것:

문서 문장
docs/01-ROLE-ARCHITECTURE.md “작곡가+가수+연주자+오케스트레이터+DJ = 1인 악단“
docs/02-MUSIC-INDUSTRY-THESIS.md “프로덕트는 공짜, 프로세스만 돈을 번다“
docs/06-ECOSYSTEM-MOAT-REPORT.md “IP of the Person — LLM이 복제 못 하는 유일한 해자”
docs/07-CYBORG-ARCHITECTURE.md “인간 물성화 + AI 무성화 = Cyborg 오케스트레이터”
docs/10-SLOT-STRATEGY.md “바순(조카) GO + 유지희(작곡가) 베타 테스터 전환”
docs/03-SOURCEPOOL.md “유튜브 피아노 채널 = 무료 편곡 하청업체”
docs/00-COPYRIGHT-AXIOMS.md “저작권은 신이 아니라 게임룰이다”

→ Boss는 방향을 새로 말한 게 아니라, 이미 써둔 것을 다시 확인한 것이다.

IP 논리 — 이건 진짜 튼튼하다

퍼블릭 도메인 원곡 → 내 편곡(내 저작권) → 내가 만든 악기 → 내 목소리
= 클리어런스 0 · 라이선스료 0 · 남의 권리 0

대부분의 프로듀서는 이 자리에 못 선다. Spitfire·Pianoteq·Native Instruments는 전부 남의 라이선스다.
렌더마다 권리가 붙는다. Boss는 그걸 자기 것으로 바꾸려는 것이고 — 그게 해자다.

3. 난이도 3분류

목표를 이렇게 잡으면 “왜 이렇게 힘든가”가 세 덩어리로 갈린다.

① 이미 풀린 것 — 더 고민할 필요 없음

  • PD 소스 수급 (IMSLP 등) — 저작권 만료 명확
  • MIDI → 렌더 — FluidSynth 80배속 실측, REAPER aarch64 헤드리스 실증(117 §6)
  • 배포 배관 — 유튜브·스포티파이·티스토리 MCP 존재
  • 편곡 자동화 — engines/daw 존재

② 진짜 어려운 것 — 도구로 안 풀림

정확히는 “녹음”이 아니라 “편집”이다. §4에서 다시 쪼갠다.

  • 가상악기 녹음 — 연주자·방·마이크. 물리적 세계. 폰이든 슈퍼컴퓨터든 무관
  • 가창 합성의 마지막 10% — RVC도 DiffSinger도 “되는 수준”까지 왔지만
    사람이 진짜 목소리로 받아들이는 상한은 아직 아무도 못 풀었다. 상용도 못 풀었다
  • 관객 — 레이블은 카탈로그만이 아니다. 기술과 무관

③ 폰 때문에 생긴 것

ABI 벽 · GUI 없음 · 도커 없음 · 램 한도(Salamander 1.18GB)

⚠️ 여기가 Boss가 답답해하던 지점이다.
③은 진짜 일이지만 ②의 병목을 향해 있지 않다.
벽은 스튜디오(방·마이크·연주자)에 있고, 우리는 폰을 붙들고 있었다.

4. 핵심 교정 — 퀴트 지점은 “녹음”이 아니라 “편집”

§3②를 다시 쪼개면 이렇게 된다. 이게 이 세션의 가장 중요한 발견이다.

단계 누가 여기서 퀴트하나 자동화 되나 Boss 새 실력이 닿나
악기 녹음 (방·마이크·연주자) 돈과 물리 ❌ ❌
악기 편집 (컷·벨로시티·루프·SFZ 저작) 여기서 90%가 퀴트한다 ✅ 됨 ✅ 정확히 여기
가창 마지막 10% 업계 전체가 못 풂 ⚠️ 부분적 ⚠️ 부분적
관객 아무도 모름 ❌ ❌

샘플 라이브러리 제작자가 도중에 관두는 이유는 녹음이 아니라 편집이다.
노트 하나하나 자르고, 벨로시티 레이어 정렬하고, 루프 포인트 잡고, SFZ 매핑하는 그 반복 노동.

그리고 그건 파일 들어가고 파일 나오는 결정적 작업이다. → 자동화 대상이다.
→ Boss가 1년 사이 강해진 지점이 정확히 여기다.

참고: Spitfire가 커진 이유 중 하나가 AUNTIE 엔진 — 편집·관리를 시스템화한 것.
Boss는 이제 그걸 만들 수 있는 자리에 있다. 1년 전엔 못 만들었다.

그리고 물리적 입구는 이미 확보돼 있다: docs/10-SLOT-STRATEGY의 바순(조카).
없는 게 아니라 아직 안 열었을 뿐이다.

5. 우선순위가 뒤집혔다 — R6의 재해석

parksy-audio 027의 R6 원문:

sfizz 명령줄 렌더 검토. Salamander 원본 SFZ(세기 단계가 SF2보다 많음)와 SSO/VSCO2를
REAPER·화면 조작 없이 렌더 …

내가 처음에 이걸 “품질 상한 조정 / 렌더 백엔드 교체”로 읽었다. 틀렸다.

SFZ = 자작 악기의 포맷이다. sfizz가 열리는지는 “내가 만든 악기를 재생할 수 있느냐” 의 문제다.
→ R6는 레이블 목표의 핵심 부품이었고, 나는 그걸 렌더 잡일로 축소해서 봤다.

그래서 순서가 바뀐다 (NPU는 여기 없다):

1. sfizz aarch64 빌드 가능한가      ← 자작 악기 재생기 확보
2. 샘플 → SFZ 파이프라인            ← 폰에서. Boss 새 실력이 맞는 자리
3. 조카 바순 녹음                   ← 물리
4. 악기 1호 완성

⚠️ 029와 어긋나는 지점 — sfizz의 용도가 둘이다

docs/dev-logs/029 §6 보류 줄:

보류 | QNN/NPU, sfizz 소스 빌드, 오케스트라 | — | 보컬 단계에서

029는 sfizz를 “오케스트라”와 묶어 보류시켰다. 그건 029의 프레임(피아노 독주 렌더 = Salamander)에서는 맞다 —
피아노만 하면 SFZ가 필요 없다.

그런데 sfizz에는 두 번째 용도가 있고, 그게 이 문서의 프레임이다:

용도 필요한 것 어느 프레임
오케스트라 SFZ (VSCO2·SSO) 남의 SFZ 재생 029 — 보류 맞음
자작 악기 (조카 바순) 내가 만든 SFZ 재생 118 — 레이블의 핵심 부품

→ 보류 자체는 맞다. 단 “sfizz = 오케스트라”로만 적히면 자작 악기 경로가 문서에서 사라진다.
→ 다음에 029를 고칠 때 보류 줄에 “자작 악기용 sfizz는 별개 트랙” 을 한 줄 붙일 것.

Boss가 말한 “레이블”과 029의 “피아노 독주 렌더”는 충돌이 아니라 순서다:
피아노로 먼저 내보내고(029), 악기는 나중에 쌓는다(118). 문제는 후자가 어느 문서에도 안 적히는 것.

6. 실측으로 찾은 문제 — parksy-audio

이 세션에서 원격 세션(parksy-audio)과 주고받으며 실측한 것.

6.1 Salamander 경로 3개가 전부 죽어 있다 [실측]

027 §4가 “박씨 결정 필요 — Salamander 정식 경로 1개 확정 (3개 중)”으로 남긴 것:

6.2 살아있는 코드가 죽은 경로를 가리킨다 [실측]

# parksy-audio/pipeline/zero_compose.py:126-127
Path('/mnt/d/PARKSY/parksy-audio/samples/Salamander Grand Piano.sf2'),   # ← 없음

“무조건 Salamander” 규칙이 있는데 렌더 코드가 두 경로 다 헛짚고 있다.
→ -91dB 무음 같은 미스터리 버그를 만드는 전형. 소리를 만드는 선에서 끊어진 곳 = 먼저 고칠 곳.

6.3 028의 과장 정정

parksy-audio 028(내가 쓴 것)에서 “026의 최대 갭을 닫았다” 고 썼다. 과장이다.
내가 렌더한 건 <SOURCE WAVE FILE "src20.wav"> — WAV 넣고 WAV 뽑은 것. 합성 경로를 안 건드렸다.
026의 갭은 MIDI → 악기 → 오디오 맥락이었다. 원격 세션의 지적이 맞다.

실증된 범위: 폰에서 REAPER가 헤드리스로 렌더 명령을 받는다 ✓ / MIDI→악기 렌더는 미검증 ✗

6.4 phantom process killer는 이 폰에서 이미 꺼져 있다 [실측]

adb shell settings get global settings_enable_monitor_phantom_procs  →  false

명시적으로 false(기본값이면 null) = 누군가 일부러 껐다. 현재 위험 비활성.
단 안드로이드 업데이트·개발자옵션 초기화로 되살아날 수 있음.

7. 폰은 이 목표에 거의 기여하지 않는다 — 정직하게

폰이 레이블 목표에 주는 것: 비용 $0 + “1인 악단”이라는 서사. 둘 다 실제 가치다.
그런데 §3②의 병목은 전혀 안 밀어준다.

폰 작업은 진짜 일이다. 근데 목표의 진짜 벽을 향해 있지 않다.

폰이 맞는 자리는 따로 있다: §4의 편집 파이프라인(샘플 → SFZ). 파일 기반 결정적 작업.
→ 폰을 버리는 게 아니라 맞는 자리로 옮기는 것.

8. 다음 부품 — 가장 작은 것

큰 그림을 다시 그리면 1년 전과 똑같이 된다. 이번엔 부품을 만든다.

바순 음 하나 녹음 (폰 마이크로도 됨)
  → 폰에서 잘라내기
  → SFZ 파일 하나로 저작
  → sfizz 또는 FluidSynth로 재생
  → 그 음이 소리 나면 끝

이거 하나면 악기 레인이 살아있는지 죽었는지 하루 안에 판정 난다.
살아있으면 그 파이프라인을 노트 88개에 돌리면 바순 악기 1호 완성.

1년 전 그림과 다른 점: 오늘 오후에 끝나고, 결과가 귀로 들린다.

9. 지금 순서 (확정 아님 · 제안)

1. sfizz aarch64 빌드 가능한가         ← 자작 악기 재생기 (반나절)
2. 샘플 → SFZ 파이프라인 (폰)          ← Boss 새 실력이 맞는 자리
3. 조카 바순 녹음 계획 (언제·어디서·무엇을)
4. 악기 1호 → 그다음 027 렌더 품질

NPU 없음. 3노드 설계 없음. QNN 없음. 그건 §3①이거나 나중이다.

10. Boss가 답답해한 것 — 기록

“우리가 지금 작업하고 있는 게 어려운 거 하고 있는 거냐? 존나 쉬워 보이는데 왜 이렇게 힘들지?”

진단:
- 어려운 일을 하는 게 아니라 어려운 자리에서 하고 있었다
- 어려운 건 ①음악이 아니라 ②Boss가 정한 조건 + ③에이전트들이 서로 안 이어지는 것
- ③의 실증: 027이 기록한 Salamander 경로 3개가 전부 죽어 있었고 아무도 몰랐다.
027 작성 2026-09-30 → 확인 2026-10-03. 사흘. 언제 죽었는지는 모른다 — 아무도 안 알아챈 게 요점.
