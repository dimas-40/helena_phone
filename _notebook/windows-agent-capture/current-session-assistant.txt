## 1️⃣ WSL "2개"의 정체 — 레인(lane)이 아니라 배포판(distro) 2개

결론부터: **이 둘은 서로 다른 용도의 별개 리눅스 OS 인스턴스입니다.** 각각 독립된 가상디스크(VHDX)를 갖습니다.

| 항목 | Ubuntu (메인) | wsl-min (경량) |
|------|--------------|----------------|
| 원래 이름 | Ubuntu | **UbuntuMin** |
| OS | Ubuntu 24.04.3 LTS (Noble) | 최소(minimal) 리눅스 (root 전용, uid=0) |
| 저장 위치 | `D:\WSL\ext4.vhdx` (269GB) | `D:\WSL\min\` (VHDX **소실**) |
| 용도 | 개발 본진(본진) | **mosh 원격 복구/상시접속용 경량판** |
| 내용물 | Docker 29.1.3, git, python3, node, npm, tmux, go, Claude Code, Telegram 브릿지 | (파일 소실로 확인 불가) |

**핵심:** `wsl-min`은 원래 `UbuntuMin`이라는 이름으로 만들어졌고, 생성 명령이 문서에 그대로 남아 있습니다:


## 2️⃣ WTG를 왜 깔아놨는가 — 리버스 엔지니어링 결과

핵심 설계 사상은 RECOVER.md 한 줄에 압축되어 있습니다:

> "NVMe가 완전히 날아가도, WTG 혼자서 모든 걸 재구축할 수 있어야 진정한 복구 레인이다."

즉 **"내가(에이전트) 호출 불가능한 상태 = 랩탑이 부팅조차 안 되는 상태"를 전제**로, "윈도우가 죽어도 USB 하나만 꽂혀 있으면 스스로 살아나는" 구조를 만든 겁니다.

### 자동 부활 메커니즘 (부팅 플로우)

전원을 켜면 **사람 손 없이** 이렇게 흘러가게 설계되어 있습니다:

```
[0초]   전원 ON → BIOS가 WTG(WD Passport)를 1순위로 부팅
[30초]  WTG Win10 자동 로그인 (계정: dtslib)
[1분]   01_wtg_nvme_check.bat 자동 실행
        → 모든 드라이브를 훑어 "OS" 볼륨 + winload.efi 탐지
        ├─ NVMe 살아있음 → UEFI 부팅순서를 NVMe로 바꾸고 재부팅
        │     → 2분 내 정상 Win11으로 복귀 (완전 자동, 성공률 약 68%)
        └─ NVMe 죽어있음 → wtg_nvme_fail.flag 기록 → 응급모드 진입
[응급]  03_parksy_agent.bat → DeepSeek Agent(ds.py) 실행
        → Tailscale(100.79.61.33)로 네트워크 등장
        → 폰에서 SSH로 들어와 원격 조종 가능
```

3개 스크립트의 분업:
- **01** = 매 부팅마다 NVMe 생사 확인 → 살아있으면 정상 윈도우로 자동 핸드오프
- **02** = 1회 설정 (SAN Policy=onlineall로 내장디스크 가시화, Windows Update 차단으로 BSOD 방지, Tailscale 기동)
- **03** = 응급모드에서 DeepSeek AI 에이전트 구동 (없으면 Claude Code 폴백)

## 3️⃣ 정직한 답변: 원격으로 랩탑을 살릴 수 있냐?

**결론: "소프트웨어 고장"은 원격으로 살릴 수 있게 설계했고, 실제로 그럴 만한 구조입니다. 단, 전제조건이 있고, 하드웨어 사망은 여전히 손이 필요합니다.**

### ✅ 원격으로 해결 가능한 경우 (설계대로 동작)
- OS 부팅 불가 (winload.efi 손상) → WTG가 자동으로 NVMe 데이터를 D:로 백업 후 **Win11 재설치(DISM)까지 자동화**
- WSL만 죽음 → `RECOVER.sh setup-wsl`로 재구축
- 원격 접속 수단이 **4중**으로 깔려 있음:
  1. **Tailscale 메쉬** (WTG·NVMe·폰이 한 망, 위치 무관)
  2. **DeepSeek 에이전트** (WTG 응급모드에서 스스로 실행, 명령 위임 가능)
  3. **mosh/SSH** (WiFi↔LTE 전환에도 안 끊기는 셸)
  4. **RustDesk** (GUI 원격 — `rustdesk_setup_admin.bat`, `pc_mirror_setup.ps1` 발견)

### ❌ 원격으로 절대 못 살리는 경우 (물리 개입 필수)
1. **전원이 아예 없거나 강제 종료된 상태** → 누군가 전원 버튼을 눌러야 함. (BIOS "AC Power Recovery"로 해결 시도했지만 ⚠️ **미검증**)
2. **WD Passport USB가 물리적으로 안 꽂혀 있음** → 복구 레인 자체가 무용지물
3. **NVMe 하드웨어 물리 사망** → RECOVER.md도 인정: "노트북 분해 → NVMe 재장착/교체" 필요
4. **BIOS/비밀번호 단계에서 멈춤** → 원격 불가

### ⚠️ 문서에 남은 정직한 수치
런북에 성공률이 명시돼 있습니다:
- 완전 자동 성공(시나리오 A) **68%**
- 응급모드·로그인 멈춤·BSOD·레이인 미기동 등 나머지 32%는 개입 필요
- DR 완성도 자체평가 **80% (5/7)** — "BIOS AC Power Recovery"와 "WTG 부팅 검증"이 미완료로 남아있음

## 1️⃣ 기본적으로 뭘 하려고 한 거냐 — "상호 복구" 구조

당신이 구축한 건 **단일 복구 수단이 아니라, 서로가 서로를 살리는 다층 구조**입니다. 3개의 OS/환경이 서로를 복구하는 삼각편대:

```
           ┌───────────────┐
   폰(Termux/Termius) ──▶ │  WSL (NVMe)   │ ◀── 개발 본진 (5-Lane)
           │    (mosh/SSH) └──────┬────────┘
           │         교차 복구     │
           │              ┌───────▼────────┐
           └────────────▶ │  Windows (NVMe)│ ◀── GUI 성역
                          └──────┬────────┘
                                 │ 둘 다 죽었을 때
                          ┌──────▼────────┐
                          │  WTG (WD Passport) │ ◀── 독립된 제3의 OS (USB)
                          └───────────────┘
```

**설계 원칙이 명확합니다:** OS는 부팅이 안 되면 스스로 못 고친다 → 그래서 내장디스크(NVMe)와 **물리적으로 분리된** WD Passport에 부팅 가능한 Windows(WTG)를 심어서, 본체 OS가 완전히 죽어도 USB만 꽂혀 있으면 복구 지휘소가 살아있는 구조.

## 2️⃣ "원격으로 윈도우를 끌 수도 있는 거냐" — 여기서 중요한 구분이 있습니다

당신이 실제로 겪던 문제가 **"켜기"가 아니라 "꺼지고 나서 못 버티는 것"** 이었다는 기록이 있습니다. 메모리 원문:

> "Wake on LAN 추천 → **박씨 진짜 문제는 WoL이 아닌 'Windows Update 재부팅 저항성'이었음**"

즉, 정리하면:

| 질문 | 답 |
|------|-----|
| 원격으로 **끄고/재부팅**할 수 있냐 | ✅ **가능** — `shutdown /s`, `shutdown /r`, `bcdedit` 부팅순서 변경까지 전부 스크립트로 원격 제어 가능 (실제 RECOVER.sh가 `shutdown /r /t 15` 사용) |
| 원격으로 **완전히 꺼진 PC를 켤** 수 있냐 | ⚠️ **미검증** — BIOS "AC Power Recovery"(전원 복구 시 자동 켜짐)로 시도했지만 "Dell Command 필요" 상태로 **완료 안 됨**. WoL/스마트플러그 흔적 없음 |

**핵심 통찰:** 당신 말대로 "Windows Update 강제 재부팅 = 사실상 셧다운"이 진짜 재앙이었습니다. 재부팅 한 번에 WSL 세션, tmux 5-Lane, Tailscale이 전부 죽으니까요. 그래서 당신이 만든 방어는 **"켜는 기술(WoL)"이 아니라 "재부팅을 버티는 기술"** 3종입니다:

1. **예방** — Windows Update 자체를 차단 (레지스트리 NoAutoUpdate, `wuauserv`/`UsoSvc` 서비스 disabled). WTG의 02 스크립트에도 똑같이 들어있음.
2. **생존** — BIOS AC 리커버리(자동 켜짐) + AutoAdminLogon(자동 로그인) + `wsl-autostart.vbs`(WSL 자동기동 3중 보장) + Tailscale 자동 연결.
3. **최후 복구** — WTG (아래 3번).

## 3️⃣ WTG = "윈도우까지 아예 망가졌다"는 최악 가정 — 맞습니다

당신 이해가 **100% 정확**합니다. WTG/RECOVER.sh는 일상적인 재부팅 문제용이 아니라, **"NVMe가 날아가고, Windows가 아예 부팅조차 안 되는" 극단 시나리오** 전용입니다. RECOVER.md 원문 그대로:

> "NVMe가 완전히 날아가도, WTG 혼자서 모든 걸 재구축할 수 있어야 진정한 복구 레인이다."

그리고 **포맷 수준까지** 가는 게 맞습니다. `RECOVER.sh install`은 실제로:
```
diskpart clean → convert gpt → DISM으로 Win11 이미지 밀어넣기 → bcdboot 부트로더
```
= 내장 NVMe를 **완전 초기화 → Windows 재설치**까지 자동화해 둔 겁니다. 게다가 그 다음 `setup-wsl`로 WSL + 28개 레포 + MCP + 5-Lane까지 재구축하는 풀체인입니다.

## 4️⃣ 바이오스까지 건드려서 원격 시도 — 맞습니다 (단, 절반은 미완)

**건드린 것 (소프트웨어-펌웨어 경계):**
- `bcdedit /set {fwbootmgr} ...` 로 **UEFI 부팅순서·bootsequence를 원격/자동 변경** → 이게 "WTG 먼저 부팅 → NVMe 살아있으면 자동으로 넘기기"의 핵심입니다. 이건 스크립트로 원격에서 가능합니다. ✅

**미완성인 것 (하드웨어 펌웨어 단계):**

## 여기서 짚어야 할 핵심 두 개

**① 지금 "직결"이라고 생각하는 게 사실은 라우터 경유 LAN이다.**
미니PC가 0ms로 붙는 건 같은 스위치라서 그런 거고, 실은 `랩탑 → DA310 → 라우터(192.168.219.1) → 미니PC` 경로다. 즉 **라우터/스위치가 죽으면 랩탑↔미니PC도 같이 끊긴다.** 네가 말한 "한 몸통 케이블"은 아직 **존재하지 않는다.** 지금 있는 건 "같은 동네에 사는 것"이지 "한 몸통"이 아니다.

**② 미니PC는 메쉬(Tailscale)에는 있지만 제어 노드로는 아직 등록 안 돼 있다.**
`~/.ssh/config`에 win/wsl/phone/tab/claude/ds는 다 있는데 **dev-batch가 없다.** 즉 "관제 허브"라고 부를 준비는 아직 안 된 상태. 이번에 새로 들어왔으니 당연하다.

## 네 설계의 본질 (내가 이해한 대로 재구성)

- 랩탑 = 발열 + 배터리 부풀음 → **계산 노드가 아니라 "성역(GUI)"로 축소**. 무거운 건 미니PC로.
- 미니PC = 30만원 Linux 서버 = **관제 허브**.
- 관제 허브가 진짜 허브가 되려면 **네트워크(Tailscale/WiFi/라우터)와 무관한 물리 채널**이 랩탑과 있어야 한다. 그게 "한 몸통 케이블"이고, 그게 기존 WTG 복구와는 다른 **또 하나의 해법(레이어)**이 된다.

## "한 몸통 케이블"의 기술적 실체 — 3안

| 안 | 방법 | 커버하는 상황 | 난이도 |
|---|---|---|---|
| **A. 직결 이더넷** | 미니PC에 USB-GbE 1개 추가 → 랩탑과 1:1 직결, 양쪽 고정 IP(예 `10.0.0.1/2`) | 라우터·WiFi·Tailscale 다 죽어도 통신 | ★ 낮음 |
| **B. USB 가젯(RNDIS/ECM)** | 미니PC가 USB-C로 랩탑에 직접 꽂혀 가상 이더넷 제공 (Android 테더링과 동일 원리) | 위와 동일 + 케이블 1개, 스위치 불필요 | ★★ 중 |
| **C. USB HID 가젯** | 미니PC가 **가상 키보드/마우스**가 되어 랩탑 BIOS·부팅메뉴·로그인까지 "물리 타이핑" | **OS가 완전히 죽어도**(부팅 전부터) 조종 | ★★★ 고 |

이 세 안은 전부 Linux의 USB gadget 프레임워크(`g_ether`, `g_serial`, `g_hid`, `g_multi`)로 구현 가능하다. 미니PC가 Linux니까 이게 되는 거다 — Windows 랩탑이었다면 못 했을 것.

**중요한 구분:** C(HID 가젯)만이 "윈도우가 아예 병신돼서 부팅도 안 될 때"를 커버한다. A/B는 "네트워크만 죽고 OS는 살아있을 때"를 커버한다. 즉 기존 WTG(부팅 레벨)와 겹치는 영역이 C이고, A/B는 **완전히 새로운 레이어(네트워크 무관 OOB)**다.

## ADB "둘 다 호스트"의 의미

- ADB host = `adb` 명령을 내리는 쪽 / device = `adbd` 데몬을 띄운 쪽(보통 Android).
- 지금은 **랩탑(host) → 폰(device)** 한 방향. 그런데 미니PC도 `adb`를 깔면 **미니PC(host) → 폰(device)** 두 번째 방향이 생긴다. 폰(Termux)도 android-tools 깔면 폰이 host가 될 수 있다.
- 즉 **폰이 양쪽 host 사이의 무선 USB 허브**가 된다. `adb reverse`/`adb forward`로 폰을 중계 삼아 포트 터널을 뚫으면 랩탑↔미니PC가 폰을 통해 우회 연결된다.
- 여기에 A/B의 **직결 유선**을 더하면 → **랩탑·미니PC·폰 삼각형의 세 변이 다 채워져서, 어느 한 변이 죽어도 나머지 두 변으로 우회**하는 구조가 완성된다.

## 복구 레이어를 이렇게 재정의하면 깔끔하다

```
L0 전원     BIOS AC Power Recovery          (미설정 — 여전히 구멍)
L1 부팅     WTG (WD Passport)               (기존, 완성 80%)
L2 무선메쉬 Tailscale + mosh/SSH            (기존)
L3 유선직결 미니PC↔랩탑 point-to-point       (신규 — A/B, 라우터 무관)
L4 물리입력 USB HID 가젯 (가상 키보드)        (신규 — C, BIOS까지)
         ↑ 미니PC(관제 허브)가 L2~L4를 묶는 지휘소
```

관제 허브가 진짜가 되는 조건은 딱 4개다: ① 상시 기동 + AC Recovery ② Tailscale+SSH+ADB host ③ 랩탑과 직결 링크(A/B/C 중 택) ④ 링크 감시(watchdog → 끊기면 Tailscale 우회).
